テスト書き方道場

仕様を読んでテストを書くと、こっそりバグを仕込んだコードをいくつ見破れたかで採点します（ミューテーションテスト）。正しいコードでは通り、バグ入りのコードでは落ちるテストが良いテストです。

      テストする関数

      正しい実装を見る

      本当のテストは仕様だけを見て書くのが基本です。どうしても困ったときに。

      
        
      
        
      
          使える書き方
          
      
            
      test("名前", () => { … })
      テストを1つ作る（it も同じ）
      
            
      describe("名前", () => { … })
      テストをまとめる
      
            
      expect(x).toBe(y)
      x と y が同じ（数・文字列・true/false）
      
            
      expect(x).toEqual(y)
      配列やオブジェクトの中身が同じ
      
            
      expect(x).toBeCloseTo(y)
      小数がほぼ同じ（小数第2位まで）
      
            
      expect(() => f()).toThrow()
      エラーが起きる。toThrow(RangeError)、toThrow("文字") でしぼれる
      
            
      expect(x).toBeUndefined()
      undefined である（toBeNull・toBeDefined も）
      
            
      expect(x).toBeTruthy()
      true 扱い（toBeFalsy は false 扱い）
      
            
      expect(a).toContain(x)
      配列・文字列に x がふくまれる
      
            
      expect(a).toHaveLength(n)
      長さが n
      
            
      expect(x).toBeGreaterThan(y)
      x > y（toBeLessThan・…OrEqual も）
      
            
      expect(x).not.toBe(y)
      .not で逆の意味
      
          
      
        
      
      
      
      
      
        
      採点のしかた（100点）
      
        
      バグ発見 80点 … 仕込まれたバグ入り版のうち、テストが1つでも落ちたものの割合。
      読みやすさ 20点 … 中身がわかるテスト名（8）、どのテストにも expect がある（6）、1つのテストの expect は4つまで（6）。
      減点 … 正しいコードで失敗するテストは、テスト側のまちがい。1つにつき −10点で、バグ発見にも数えません。
